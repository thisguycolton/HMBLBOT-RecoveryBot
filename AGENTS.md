# AI Agents Guide - RecoveryBot

This guide provides essential architectural and operational knowledge for AI agents working on the RecoveryBot codebase.

## 🏗 Architecture Overview
RecoveryBot is a Ruby on Rails 7 application designed to support recovery and 12-step programs.

### Tech Stack
- **Backend**: Ruby on Rails 8, PostgreSQL
- **Frontend**: React components (JSX) integrated with Stimulus.js and Vite for bundling.
- **Deployment**: CapRover / Docker

## 📂 Key Components & Logic

### 📚 Literature Library
Manages recovery literature (Books, Chapters, Readings).
- **Models**: `Book`, `Chapter`, `Reading`
- **Logic**: Literature is structured hierarchically. Imports and exports are handled via JSON payloads in `Api::BooksController` and supported by services like `LiteratureImporter`.
- **Frontend**: Uses rich text editors (Tiptap/Lexical) for content management (`ChapterEditor.jsx`, `ReadingEditor.jsx`).

### 🗣 Topicificator & Hostificator
- **Topicificator**: A randomized topic generator for group discussions. Uses `TopicSet`, `TopicCategory`, and `Topic` models.
- **Hostificator**: A voting system for proposing and selecting hosts/proposals (`Hostificator`, `HostProp`, `HostVote` models).

### 🎮 Quest System (Game Logic)
An API-driven system for tracking game state, inventories, and player progress.
- **Models**: `QuestPlayer`, `QuestSession`, `QuestInventory`
- **API Endpoints**: Located in `app/controllers/api/v1`. Handles player creation, session joining (via `join_code`), and game state persistence (grid position, points, inventory).

### 🤝 Groups & Meetings
- **Models**: `Group`, `GroupMembership` (roles `admin`/`member`, status `active`/`requested`), `Meeting` (weekly: one row per weekday, or once), `GroupBook` (approved literature), `OiaaMeeting` (cached OIAA directory).
- **AA Intergroup**: called "AA Intergroup" everywhere people see it (internally still `Oiaa*`). `OiaaFeed` reads its Meeting Guide JSON feed (https://data.aa-intergroup.org/, or `AA_INTERGROUP_FEED_URL`) into `oiaa_meetings`, in the background at boot and when a week old. Meetings linked by `oiaa_slug` refresh from it; `bin/rails aa_intergroup:sync` fetches it by hand.
- **Access**: admin-only while it's tried out (`Group.feature_open_to?`); `GROUPS_FOR_EVERYONE=1` opens it to every account. People already in a group always see it.
- **Frontend**: React app at `/groups` (`entrypoints/groups.jsx`, `components/groups/`), JSON under `/api/groups`. The profile page (`/users/edit`) is `entrypoints/profile.jsx`.
- **Court verifications**: `/court_verifications/new?group=<slug>` is a group's own form (unlinked, like the plain one).
- **Group pages**: a group's Home tab is laid out in the HMBLBOT Editor (`/groups/:slug/page/edit`, group admins), the same editor events use (`components/events/editor/EditorFrame.jsx`). Blocks live in `groups.page_blocks` (nil = the default page, `GroupPageTemplate`, which site admins edit at `/groups/default-page/edit`); `EventBlocks::GROUP_TYPES` adds the group's own blocks, and every block has a palette `color`. AA Intergroup groups not here yet show the default page at `/groups/find/:oiaa_slug`. `GroupPage` (app/services) builds the JSON.
- **Group conscience** (`/groups/:slug/conscience`, members' tab; plan in `docs/group_conscience_plan.md`): steps 1 (Documents), 2 (Decisions), 3 (Business meetings) and the plan's step 4 except online voting (Service, Treasury) are built; sections of the tab: Overview, Meetings, Decisions, Documents, Elected officials (`/conscience/officials`; `/service` still opens it), Treasury. `GroupDocument` (kinds are the folders; `visibility` public/members/keepers; `status` draft/current/archived; `body` and/or an Active Storage `file`: PDF, DOCX, XLSX, pictures, 20 MB; `body_format` `html` (written in the Tiptap editor, cleaned on save by `DocumentHtml`) or an older `markdown`, converted when first opened in the editor) with `GroupDocumentVersion` keeping the copy each save replaced (`GroupDocument#revise` / `#restore`). **Record keepers** are members with `group_memberships.can_keep_records` (switched on in the Members tab); `Group#records_editable_by?` = admins, site admins and keepers. `GroupDocument.visible_to(group, user)` is the one place that decides who sees what: visitors get current Public documents, members also Members ones, keepers everything. JSON under `/api/groups/:slug/documents` (`Api::GroupDocumentsController`, files served through it so visibility is enforced); UI in `components/groups/conscience/`: a document is a page (`DocumentPage.jsx`, `DocumentToolbar.jsx`, `editorKit.js`, `documents.css`) that record keepers edit in place, with Share link (`ShareMenu.jsx`) and Save as PDF (the browser's print, styled in `documents.css`) in the top bar; Word (.docx via mammoth) and RTF (`lib/rtf.js`) files import into it (`lib/documentImport.js`, in the browser), and PDFs are read in the page with pdf.js (`PdfViewer.jsx`). The `documents` HMBLBOT Editor block lists what the viewer may see, so a group can put its format on its public page. **Decisions**: `Motion` (table `motions`; status proposed/passed/failed/tabled/withdrawn, counts as counted in the room (nil for backfilled ones), `supersedes_id` for what it replaces, `minority_opinion`, category, `visibility` members/public). A passed motion no later passed motion replaces is **standing** (`Motion.standing`), unless it is marked `one_time` (done once, like a script edit: kept in the log, not listed as standing; toggle in `DecisionForm`, bulk `one_time`/`standing`). `Motion.visible_to(group, user)`: visitors get Public decisions that passed, members Members and Public, keepers everything. `/api/groups/:slug/motions` (`Api::GroupMotionsController`; keepers write, group admins delete), UI `components/groups/conscience/DecisionsView.jsx` / `DecisionForm.jsx` at `/conscience/decisions`. A document can name the decision that adopted it (`group_documents.approved_by_motion_id`). The `decisions` HMBLBOT Editor block lists standing decisions the viewer may see.
  - **Business meetings**: `BusinessMeeting` (date, `starts_at` kept in the group's zone via `set_start`, status planned/held/cancelled, minutes as sanitized HTML with `minutes_status` draft/posted/approved, optional `event_id` and `meeting_id`) with `AgendaItem`s (members' suggestions come in as `suggested`; record keepers approve, reorder, cross off). `BusinessMeeting.visible_to`: record keepers see all, members the `members` ones, nobody else any; draft minutes stay out of the JSON until posted. A decision links to its meeting and agenda item (`motions.business_meeting_id`/`agenda_item_id`; recording one on an agenda item settles it). Notifications: record keepers when a member suggests an item, members when a meeting is scheduled and when minutes are first posted. `Api::GroupBusinessMeetingsController`/`GroupAgendaItemsController`, overview at `GET /api/groups/:slug/conscience`. A group admin can have a draft `Event` made (with a `conscience_agenda` event block, whose live agenda `EventsController#blocks_for_viewer` fills in for members only); the `business_meeting` HMBLBOT Editor block shows members the next one's agenda (and a way to suggest an item), and visitors only a meeting a *published* event announces. UI: `MeetingsView`, `MeetingPage` (agenda, decisions, minutes in the document editor, print sheet), `OverviewView`.
  - **Elected officials** (the Service tab, renamed; internal names stay `ServicePosition`/`ServiceTerm`): `ServicePosition` (term length, sobriety minimum) and `ServiceTerm` (a plain-text name; optional `user_id` so the holder hears when it's up). Starting a term ends the one before it. `ServiceRotation.remind_group!` tells record keepers (and the holder) once per term when it's ≤30 days from ending with nobody after it; it runs when a member opens Service or the Overview, and `bin/rails group_service:remind` does every group (there is no job runner).
  - **Treasury**: `TreasurerReport` (one per month; money in whole cents as `opening_cents`/`reserve_cents`/`lines`; `splits` share what's above the prudent reserve; `#summary` does the sums and `summarize()` in `ReportPage.jsx` mirrors it). Members read posted reports; keepers keep drafts.
  - **Robert's Rules** (the group runs meetings by them and votes in the room; the app only *records*, so there is no online voting and nothing is ever blocked): `MotionKinds` lists every kind of motion with what the rules say about it (second, debatable, amendable, vote needed, rank, effect on the motion it applies to) and is sent to the UI with the motions list. A `Motion` has a `kind` (default `main`), a `parent_id` (what it applies to), `vote_method`, an optional bylaws `required_vote`, `previous_notice`, `committee`, `postponed_to`, `amended_text` and `note`. `Motion#warnings` (record keepers only; `POST /api/groups/:slug/motions/check` gives them while typing) says where a record doesn't follow the rules: no second, the count doesn't carry it (majority of votes cast, a tie is lost, abstentions don't count; two thirds; appeals: a tie sustains the chair), a two-thirds vote taken by voice, out of precedence order, no quorum. `Motion#apply_effect!` has a passed table/refer/postpone/take-from-table/reconsider/amend change its parent; only `main` and `rescind` are *decisions* (`Motion.decisions`/`standing`; the log, Overview and page block), the rest is "procedure". Tabled, referred and postponed motions come back as unfinished business (`BusinessMeeting#unfinished_business`, carried onto an agenda via `agenda_items.motion_id`). `groups.quorum_count`/`quorum_percent` (group admins set it on the Meetings page) flag a meeting with fewer people (`BusinessMeeting#quorum_met?`); meetings also keep called-to-order and adjourned times. UI: `DecisionForm.jsx` (any kind), `DecisionsView.jsx` (Procedure filter, nested motions), `MeetingPage.jsx` (`MotionTree`), `RulesTable.jsx`.
  - Dates sent as `"2026-03-03"` are read as that day in the browser (`parseDay` in `conscience/lib.js`), not as midnight UTC. Printing (`usePrintable`, `documents.css`) shows only a page's own sheet.
- **Timeline notes**: `TimelineNote` (Markdown like highlight notes, up to 6 pictures) on a member's timeline, which is the Timeline block of their profile; shared to their groups (`TimelineNoteShare`), members see them in a group page's Timeline block. UI in `components/notes/` (NoteEditor, FeedItem, VisibilityPicker).

- **Hosts** (`/groups/:slug/hosts`, members-only tab, `HostsTab.jsx`; kept apart from elected officials because a group has dozens of weekly meetings): every weekly `Meeting` row has a **host** and a **co-host** place. `MeetingHost` (role `host`/`co_host`, plain-text `name`, optional `user_id`, `starts_on`/`ends_on`) and `MeetingHostCover` (someone covers one date, which must be a day the meeting runs). `HostSchedule` (app/services) builds the JSON and the open-places summary; `Meeting#series` groups the same meeting on every day, and `all_days` on create assigns the whole series. `/api/groups/:slug/meeting_hosts` and `/meeting_host_covers` (`Api::GroupMeetingHostsController`, `Api::GroupMeetingHostCoversController`). Schedulers are group admins and members with `group_memberships.can_schedule_hosts` (`Group#hosts_editable_by?`); a linked member is notified (`meeting_host.assigned`, `meeting_host.covering`). Record keepers/schedulers see open host places on the conscience Overview. Members marked **can host** (`group_memberships.can_host`, set by group admins in Members or host coordinators in the Hosts tab's "Who can host"; `Group#can_host?` also counts schedulers and record keepers) read documents with the `hosts` visibility (the format, linked at the top of the Hosts tab) and are the ones told when a sub is needed (`Group#host_pool`, plus schedulers; every member if nobody is marked). Whoever holds or covers a place on a date can ask for their own sub ("I can't make it") and call it off. **Host accounts**: a host coordinator connects a name on the schedule to a member's account everywhere it's written (`POST .../meeting_hosts/link`, "Connect account" in the Hosts tab). `HostCommitments` (app/services) is a person's hosting: groups where they're marked can host or hold a place, their meetings and coming dates (`User#host?`, `data-host` on `<body>`). Hosts get a Hosting section in account settings (`users.host_reminders`, `host_reminder_hours`, `host_reminder_email`; off by default) and `HostReminders` sends a notification (+ `HostMailer` email) once per date (`meeting_host_reminders`), from a thread started in `config/puma.rb` every 10 minutes, or `bin/rails meeting_hosts:remind`. Their account menu has "Court verification" (`nav/HostCourtModal.jsx`, `/api/hosting`), opening `/court_verifications/new?group=<slug>&meeting=<id>` with that meeting and their name filled in. A group's page lists who hosts the next meeting (`GroupPage#meetings`) unless `groups.show_hosts_publicly` is off (Group settings).
- **Hosting Command Center** (`/groups/:slug/host` picks a meeting, `/groups/:slug/host/:meeting_id` takes the whole window; `components/groups/hosting/`): for people who can host (`Group#can_host?`). A `HostingKit` (one per meeting, covering its whole `series`, or the group's default with `meeting_id` nil; `HostingKit.for(meeting)`) names the script (a `GroupDocument` hosts can read, cut into sections at its top headings in the browser, `scriptSections` in `hosting/lib.js`), its `HostChatPosting`s (title, Lucide `icon` from the topicificator's `IconPicker`, `minute` into the meeting, `body` copied as written with `{{meeting}}`-style placeholders) and `readings` (library chapters or links). Host coordinators (`Group#hosts_editable_by?`) set it up from the gear (`KitEditor.jsx`). `HostingSession` (one per meeting row and date) is the shared live state: section, completed sections, timer, who copied which posting, and a short `log`; `HostingPresence` is who has it open and what they're on. The page polls `POST .../ping` every 3 seconds (Action Cable isn't set up in production), `HostingCenter` (app/services) builds the JSON and picks the date (the meeting on now, ended within an hour, or the next one). Its court verification quick action opens `/court_verifications/new?group=&meeting=&host=` with that meeting and host filled in. **Reading / activity**: a script gets a section of its own for the day's reading or activity, after the paragraph `hosting_kits.activity_anchor` begins (nil: the "You choose the format!" line is found by itself, `AUTO_ANCHOR`; "none": no spot); scripts with no headings are cut at their bold time cues ("(Top of the hour)"). The hosts pick what fills it each day (`hosting_sessions.activity`, `HostingSession.tidy_activity`, `Activity.jsx`): a chapter, today's page of any daily book (a chapter slugged like `october-20`: Daily Reflections, The Language of Letting Go…), Topicificator topics (drawn on the server, `draw_topic`), a speaker, a meditation or anything else; `{{activity}}` names it in chat postings. **Service and milestones** (Host Helper's scratch paper): `hosting_kits.service_roles` ([{ key, label }], nil: `HostingKit::DEFAULT_SERVICE_ROLES`, edited in the gear) are the service the hosts line people up for; they type names under "Before we begin" (`hosting_sessions.service`, `Service.jsx`; host and co-host start from the schedule), and `{{ service_KEY }}` in the script or a posting becomes that name (`fillRoles`/`fillPosting` in `lib.js`). `hosting_sessions.milestones` ([{ id, name, length, done }]) is who's counting days or celebrating, in the sidebar. **Short link**: each `HostingSession` has a `code` (`/h/CODE`, `HostingLinksController`), shown under "Share with your co-host". Someone who can host lands on that date's Command Center (`?on=YYYY-MM-DD`, which `HostingCenter` takes as `on:` and every API call passes along); anyone else, no account needed, on `/groups/:slug/chat/:code` (`GuestPostings.jsx`, `GET /api/hosting_links/:code`, `HostingCenter#public_json`): the chat postings to copy, what's been posted and the timer, unless the kit's `public_postings` is off.

### 👤 Profiles & follows
- `/people/:username` (`/people/me` is yours), React app `entrypoints/people.jsx`, JSON from `ProfilePage` (app/services) via `Api::PeopleController`. Same access as Groups (`User.profiles_open_to?`), signed-in only, never public on the web.
- Every user has a `username` (made from their name, changeable in settings). Their page is laid out in the HMBLBOT Editor at `/people/me/edit` (`users.page_blocks`, nil = `ProfilePage::DEFAULT_BLOCKS`; `EventBlocks::PROFILE_TYPES`: feed, about, groups, people plus heading/notes/photo/gallery).
- `Follow` (no approval; the followed person gets a notification). `/people` is the home page people land on after signing in (`after_sign_in_path_for`): Notes (yours and what people you follow share) in two thirds, and a third (folded on phones) with next meetings, sobriety birthdays and events from their groups (`PeopleHome`).
- `Visibility` concern on notes and highlights: `private` (default) / `followers` / `public` (shown as "Members": anyone signed in who can see profiles). New ones take `users.default_highlight_visibility` / `default_note_visibility` from settings. Highlight share links work whatever this says.

### 🔒 Privacy, contact and sign-up
- `/privacy` (`PrivacyController`, `components/site/PrivacyPage.jsx`) describes what the app really collects, every cookie and local-storage key, and each outside service. Change it (and its date) in the same change whenever you add a cookie, a tracker, an outside service or a new kind of personal data.
- No cookie banner: every cookie is first-party and needed; Ahoy runs cookieless (`Ahoy.cookies = :none`) with masked IPs.
- `/contact` (`ContactsController`) saves a `ContactRequest` (admin suite > Contact requests, `Api::Admin::ContactRequestsController`, `ContactRequestsPage.jsx`; open/handled) and `ContactMailer` emails it to support@hmblbot.com. Sign-up (`Users::RegistrationsController`) and contact go through `HumanCheck` (decoy field + signed form time, plus an "I'm not a robot" box: ALTCHA, a proof-of-work puzzle we sign and check ourselves (npm `altcha` widget in `HumanCheckFields.jsx`; each solution is good once via `Rails.cache`), or Cloudflare Turnstile instead when `TURNSTILE_SITE_KEY`/`TURNSTILE_SECRET_KEY` are set) and a `rate_limit`. Tests post `human_check_params` (which includes a solved puzzle).
- `/terms` (`TermsController`, `components/site/TermsPage.jsx`): terms of use, linked from the footers, the privacy policy and the sign-up form ("By signing up you agree…"). Change its date when you change it.
- Sign-up uses Devise `:confirmable`: people confirm their email (link good for 3 days, resend at `/users/confirmation/new`) instead of waiting for admin approval. The old `users.confirmed` flag is kept in sync with `confirmed_at` (`User#sync_confirmed`), so queries on it still work and `confirmed: true` in code or fixtures means confirmed. Email changes wait for the new address to be confirmed (`unconfirmed_email`).
- People delete their own account on the profile page (`DELETE /api/profile` with their password); an account with readings is refused and pointed to /contact.

### 🛠 Services
Business logic for complex operations (e.g., importing literature) is encapsulated in `app/services`.

## 🚀 Development Workflow

### Local Setup
- **Server**: Run `bin/rails s` and `bin/vite dev` (there is no `bin/dev`; `Procfile.dev` lists both).
- **Database**: Use `rails db:setup` for initial configuration.

### API Structure
- `/api/...`: General resource APIs (e.g., `Api::BooksController`). Some endpoints require administrative privileges (`require_admin!`).
- `/api/v1/...`: Specialized API for the Quest game system.

## ⚠️ Important Notes
- **Admin Access**: Many critical endpoints in the API and administrative panel require `admin` status on the `User` model.
- **Data Integrity**: When importing literature, ensure slugs are unique and formatted correctly to avoid collisions.
- **React Integration**: Frontend components are located in `app/javascript/components` and are rendered within Rails views.
